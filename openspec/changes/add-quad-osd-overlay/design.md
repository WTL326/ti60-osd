# Design

## Context

动机见 `proposal.md` — Why。此处只记录塑造方案的现状与约束。

**管线位置**：`VideoHorizontalFlipYuv422` → `HyperRamMaskOverlayYuv422` → `HyperRamVideoBt656`
→ `Adv7391Top` → CVBS。叠加模块工作在 `clk`（100 MHz），下游 BT.656 序列化在 `clk_da`（27 MHz），
两者之间的 CDC 由 `HyperRamVideoBt656` 内部的异步 FIFO 承担。

**当前实际生效的形态**（已核对 RTL，与部分文档不符）：

- `src/top.v:493` 将 `rtl_mask_mode` 硬接 `1'b0` → `raw_mode=0` → 模块走 **legacy 全屏分支**，
  从 `0x0040_0000`/`0x0050_0000` 读 720×576 画布。RTL 侧注释（`top.v:1774`）确认这是有意为之：
  软核把画布写进自己的工作区。
- `docs/architecture.md:286` 与 `docs/SOFTCORE_DESIGN.md:175` 却把该画布写在 `0x00A00000`。
  **RTL 是对的，文档是错的**（`top.v:1827` 的避让注释与 `SOFTCORE_DESIGN.md:598` 的链接脚本
  `ORIGIN = 0x00400000` 互相印证：画布与软核工作区共用同一段 HyperRAM，并非冲突）。
- `docs/architecture.md:283` 称"半透明掩膜"，但 `HyperRamMaskOverlayYuv422.v:161` 实际是
  **1-bit 硬替换**（`mask_byte != 0` → `16'h80EB`），位图的 8 bit 只被当作零/非零使用。
  **当前 RTL 没有 alpha**。

**缓存现状**（`HyperRamMaskOverlayYuv422.v:45-62, 115`）：2 个 bank × 256 字节乒乓缓存，
预取地址写死为 `next_block_addr = block_addr + 256`，**假定单一顺序行扫描**。
`src/top.v:158` 的 `s_ready = can_forward && m_ready` 意味着 cache miss 会直接阻塞视频流，
模块自身注释（`:47-50`）已警告这类阻塞可能撑爆 scaler 侧 CDC FIFO。

**控制现状**：`MaskControlRegs`（`0xE1043000`）→ `ConfigSnapshotCdc #(.WIDTH(2))`（`top.v:1053`）
→ `top.v:1431-1432` 的控制源 mux → 叠加模块。提交协议为 toggle + 帧边界 ack
（`top.v:1090-1098` 的 3 拍 settle + `flip_output_sof`）。

**资源现状**：两个 bank 是异步读，被 Efinity 映射到 logic memory 而非 BRAM
（`outflow/EFX.warn.log:77-78`，每 bank 2048 bit）。

---

## Goals / Non-Goals

**Goals:**

- 4 路窗口在同一路视频上叠加，几何/使能/缓冲均运行时可配，不重新综合。
- 缓存资源**不增长**，且不因窗口跳转引入超出预算的视频流阻塞。
- RTL 侧契约（区域地址 + 寄存器映射 + 位图格式）清晰到足以让固件与上位机独立实现。
- 顺带消除文档与 RTL 的两处失真，避免后续维护者被误导。

**Non-Goals:**

- 不引入 alpha 混合、半透明、调色板或彩色 OSD（决策：保持 1-bit 纯白替换）。
- 不做硬件重叠检测/裁剪/优先级仲裁（决策：软件保证不重叠）。
- 不实现字符/字库 OSD（决策：内容是上传的位图）。
- **不改动软核固件**（源码不在本仓库），只定义它必须遵守的契约。
- 不做 4 路窗口之间的 z-order 或混合叠加。

## Decisions

### D1: 保持 1-bit 替换，不引入 alpha

**选择**：沿用 `mask_byte != 0 → 16'h80EB`，位图的 8 bit 仍只作零/非零判定。

**理由**：用户明确选择"保持 1-bit 替换"；且现有语义、上位机位图生成工具、板级观感均不变，
把风险集中在窗口化这一件事上。

**否决的替代方案**：
- *每像素 alpha*（用字节值做混合系数）：位图已是 8-bit，硬件代价小，但会改变画面观感
  （出现半透明边缘），且需重新标定上位机生成的位图，超出本次范围。
- *全局 alpha 寄存器*：新增一个需要联调的寄存器，收益不明。

> 决策记录：用户最初的诉求是"共享 alpha"，但核对 RTL 后发现**当前并无 alpha 可共享**，
> 故落地为"共享同一替换行为"。

### D2: 统一为 4 窗口逻辑，删除 legacy / raw 双寻址

**选择**：删除 `raw_mode`、`mask_left`、`mask_top` 端口与 `MASK0/1_BASE`、`RTL_MASK0/1_BASE`、
`RAW_MASK_*` 参数，以及 `HyperRamMaskOverlayYuv422.v:91-108` 的双寻址分支。
4 路窗口用同一套"基址 + 行跨距 + 窗口内偏移"寻址。

**理由**：用户选择"完全替换为 4 路"。两套寻址并存会让地址生成逻辑出现两条近似路径，
而 legacy 分支的"输出边界即画面边界"恰好是 4 窗口逻辑在窗口等于全屏时的特例，
统一后总逻辑量反而下降。

**否决的替代方案**：
- *保留 legacy 并存*：逻辑与寄存器最复杂，且 legacy 分支当前是唯一生效路径，
  保留它等于保留一个必须同步维护的第二套行为。
- *legacy 降级为占满全屏的窗口 0*：行为兼容性最好，但用户明确要求"完全替换"，
  且 512×288 的上限会让"全屏窗口"无法用同一套寄存器表达，反而要引入特例。

### D3: 内存布局与行跨距

**选择**：位图区 `0x00A0_0000–0x00BF_FFFF`（2 MiB），
`base(i, buf) = (buf ? 0x00B0_0000 : 0x00A0_0000) + i * 0x0004_0000`，
**行跨距固定 512 字节**，每路每缓冲 256 KB。

| 路 | Buffer A | Buffer B |
|---|---|---|
| OSD0 | `0x00A0_0000` | `0x00B0_0000` |
| OSD1 | `0x00A4_0000` | `0x00B4_0000` |
| OSD2 | `0x00A8_0000` | `0x00B8_0000` |
| OSD3 | `0x00AC_0000` | `0x00BC_0000` |

**理由**：
- 该区域已被 `docs/memory_axi.md` 标注为"RTL 掩膜 A/B"，重新划分不新增占用；
  同时避开软核工作区（`0x0040_0000–0x007F_FFFF`），不需要与固件团队协商边界。
- 512×288 → 288×512 = 147 456 B ≤ 256 KB，留有余量；2 MiB 恰好用满。
- **行跨距 512 是 256 的倍数，且每路基址 256 KB 对齐**，因此每个窗口行首天然 256 字节对齐。
  这使 `block_addr` 的原有算法（`{pixel_addr[31:8], 8'b0}`）**无需改动**，
  且"窗口 j 在某行的首块地址"可直接写成 `base_j + (display_y - top_j)*512`，无需取整运算。
- 代价：宽度小于 512 的位图会浪费 HyperRAM（如 128 宽的位图占 512 B/行），
  但 HyperRAM 在本布局下不紧张，换取地址生成的简洁是划算的。

**否决的替代方案**：
- *紧凑行跨距（= width）*：省 HyperRAM，但行首不再 256 对齐，块地址需除法/取整逻辑，
  且窗口首块地址依赖 width，地址生成组合逻辑显著变复杂。
- *放 `0x0040_0000`（软核工作区）*：需与固件协商边界，耦合度高。
- *放 `0x0080_0000`（文档标"保留"）*：仅 2 MiB 且按 256 KB 分配刚好占满，无余量。

### D4: 缓存不变，预取地址推广为"扫描序下一块"

**这是本次变更的核心设计。**

**选择**：保持 2 bank × 256 字节乒乓缓存**完全不变**，只把
`next_block_addr = block_addr + 256` 替换为按优先级计算的"扫描序下一块"：

1. 当前窗口在本行还有下一个 256 字节块 → `block_addr + 256`
2. 否则本行存在更靠右的使能窗口 → 该窗口本行的首块 `base_j + (display_y - top_j)*512`
3. 否则下一显示行中首个使能窗口的首块（因 `FLIP_VERTICAL_COORDS=1`，下一行 = `display_y - 1`）
4. 否则不预取

**理由**：
- 窗口**两两不重叠**（D5 的软件保证），所以任一像素至多属于一个窗口 → 2 bank 乒乓依然成立，
  **缓存容量与逻辑 RAM 占用不变**（维持 4096 bit）。
- 每次预取都在消费前一块的**同时**发起，块消费耗时 = 256 像素 ≥ 256 个 `clk`；
  一次 256 字节 AXI 突发远小于此，因此 D3 的块对齐保证下，预取足以隐藏取数延迟。
- 规则 3 让行与行之间也预热，把冷缺失压到"整个帧第一行"级别。

**否决的替代方案**：
- *每路一个独立 bank（4 或 8 bank）*：地址判定最简单，但逻辑 RAM 翻 2–4 倍
  （现有 2 bank 已被映射到 logic memory），512×288 上限下每路需 2 个 256 B 块，
  8 bank = 16 384 bit，对 Ti60 是实质新增压力。
- *每路一个行缓冲*：同样 16 384 bit，且宽度小时浪费更多。
- *不做预取，miss 时才取*：直接复现模块注释警告的逐 miss 阻塞，
  4 路窗口会让每行出现多次阻塞，有撑爆 scaler CDC FIFO 的实际风险。

### D5: 单次 commit + 单次 apply，每路独立 buffer_select

**选择**：沿用**一套** `ConfigSnapshotCdc`（`WIDTH` 由 2 加宽到 **193**）与**单一**提交/生效时点
（仍在 `flip_output_sof` 处应用）；但每路各有自己的 `buffer_select` 位。

**理由**：用户要求"每路独立 A/B"。独立性由**每路各自的 buffer_select 位**提供
（上位机可只改第 2 路的选择、其余三路保持原值一并提交），
而"原子提交"避免了 4 路版本不一致的中间帧——这是 OSD 这类叠加层不可接受的观感缺陷。

**位宽构成**：每路 `1 enable + 1 buffer + 12 left + 12 top + 11 width + 11 height = 48`，
4 路 = 192，加 `1 global_enable` = **193**。`ConfigSnapshotCdc` 按 `WIDTH` 参数化且本就做
多位原子快照，**模块本身无需改动**。

**否决的替代方案**：*每路一套 CDC、独立 apply* — 4 倍同步逻辑，且允许 4 路在不同帧生效，
会出现"部分 OSD 新版、部分旧版"的中间帧。

### D6: 寄存器映射

**选择**：在 `MaskControlRegs`（`0xE1043000`）内扩展，共 20 个字：

| 偏移 | 名称 | R/W | 内容 |
|---|---|---|---|
| `+0x00` | `COMMAND` | W | bit31 commit，bit0 global_enable |
| `+0x04` | `STATUS` | R | `{commit_count[15:0], 12'd0, pending, 1'b0, applied_global_enable}` |
| `+0x08` | `CANVAS` | R | `{16'd720, 16'd576}`（保持原样） |
| `+0x0C` | `ACTIVE` | R | `{24'd0, applied_enable[3:0], applied_buffer_select[3:0]}` |
| `+0x10 + 16*i + 0x0` | `OSD[i].POS` | W | `{8'd0, top[11:0], left[11:0]}`，均为**有符号** |
| `+0x10 + 16*i + 0x4` | `OSD[i].SIZE` | W | `{10'd0, height[10:0], width[10:0]}` |
| `+0x10 + 16*i + 0x8` | `OSD[i].CTRL` | W | `{30'd0, buffer_select, enable}` |
| `+0x10 + 16*i + 0xC` | — | R | 保留，读 0 |

**理由**：
- 沿用既有 commit 语义（写 COMMAND bit31 才发布；`pending` 未清时拒绝再次 commit），
  上位机现有的"写寄存器 → 提交 → 轮询 pending"流程无需改结构，只多写几个寄存器。
- `left/top` 取**有符号 12 bit**，保留 legacy/raw 时代既有的**负偏移越界裁剪**能力，
  上位机可把窗口部分移出画面而不必自己做裁剪。
- `width/height` 取 11 bit：`width` 需容纳 512（10 bit 够，11 bit 留余量），
  `height` 需容纳 288（9 bit 够）。统一 11 bit 便于解码与回读。
- 20 个字远在现有一拍 AXI 端点的 `read_addr[11:2]` 可寻址范围内。

### D7: `rtl_mask_mode` 语义收窄

**选择**：**保留** `rtl_mask_mode`（当前硬接 `1'b0`），但语义由"寻址模式选择"
收窄为"**OSD 控制权 / 位图上传者选择**"（RTL UART 状态机 vs 软核 AXI 路径）。

**理由**：这是两条用户决策的调和点——"完全替换为 4 路"要求删掉 raw/legacy 的**寻址**分支，
而"两条上传路径都支持"要求保留一个**选择上传者**的开关。二者并不矛盾：
寻址统一，控制源仍可切换。

**影响**：`src/top.v:504`、`:742`、`:1417` 处对 `rtl_mask_mode` 的使用需复核
（其中 `:504` 的 `riscv_uart_rx` 选择与 `:1417` 的 `mask_reply_tx` 选择仍成立）。

### D8: 模块与文件不改名

**选择**：保留 `HyperRamMaskOverlayYuv422.v` / `HyperRamMaskOverlayYuv422` 名称。

**理由**：该模块仍然是"由 HyperRAM 支撑的、对 YUV422 流做掩膜式叠加"的模块，名称未失真到有害；
而改名要同步 `ivlab239.xml:31` 与 4 处文档引用，是纯 churn，且会让本次 diff 难以审查。
若后续确有改名需求，应作为独立变更处理。

### D9: 顺带修正文档失真

**选择**：在本次变更内修正 `docs/architecture.md:283`（alpha 表述）、
`:286`（掩膜地址）、`docs/memory_axi.md:11-18 与 :211`（内存表）、
`docs/CLAUDE.md`、`src/README.md` 中与本次改动相关的描述。

**理由**：这两处失真（"半透明"与错误地址）会直接误导实现者——
本次改动正是在核对它们时才发现 RTL 与文档不一致。留着它们，下一个人还会踩。

## Risks / Trade-offs

- **预取规则 2/3 组合逻辑变深** → 在 100 MHz 下新增了跨 4 路的比较与 mux。
  缓解：先在单元仿真确认功能，再在 Efinity 综合后复核
  `docs/timing_resources.md` 的时序余量；若紧张，可把"下一块地址"打一拍寄存
  （预取本就提前 256 拍发起，寄存不影响正确性）。
- **逻辑 RAM 未增长但组合逻辑变复杂，可能改变 Efinity 的映射结果** → 缓解：
  综合后对照 `outflow/EFX.warn.log` 确认两个 bank 仍被识别为 memory block，
  未被展开成触发器。
- **512 行跨距在窄位图下浪费 HyperRAM** → 已接受；2 MiB 布局下有 256 KB/路/缓冲的余量，
  即使 4 路都用 512×288 也只占 1.125 MiB。若未来需更多路，行跨距策略需重新评估。
- **软件保证不重叠是一个"无硬件兜底"的约定** → 一旦上位机配错，画面出错且无任何错误反馈。
  缓解：`ACTIVE` 寄存器回读每路实际生效的几何，上位机可在下发后自查；
  并在上位机侧实现重叠校验（属仓库外工作）。
- **删除 legacy 全屏掩膜破坏向后兼容** → 缓解：见 Migration Plan；这是用户明确要求的破坏性变更。
- **固件源码不在本仓库，契约可能落地不一致** → 缓解：把区域地址、寄存器映射、位图格式
  （每像素 1 字节、行跨距 512）作为 spec 级契约固定下来；固件侧改造列为外部依赖并在验收时联调两条路径。
- **`ConfigSnapshotCdc` 从 2 bit 加宽到 193 bit** → 宽快照的同步链更长、面积更大，
  但该模块本就是为多位原子快照设计的。缓解：复核 `top.v:1090-1098` 的 3 拍 settle
  在加宽后是否仍足够（同步级数未变，预期仍成立），并在仿真中验证帧边界原子性。

## Migration Plan

1. **RTL 先行**：先落 `HyperRamMaskOverlayYuv422.v` + `MaskControlRegs.v` + `top.v`，
   此时旧上位机不再能配置 legacy 全屏掩膜（该功能按设计移除）。
2. **单元验证**：新写自检测试平台通过后，再进综合与板级。
3. **板级验证**：按 `docs/CLAUDE.md:255-263` 清单回归，并通过 VIO 观察新增诊断。
4. **上位机与固件同步**：按 D6 寄存器映射与 D3 内存布局改造；
   两条上传路径各联调一次。
5. **文档收尾**：完成 D9 的文档修正。

**回滚**：本次改动集中在 3 个 RTL 文件 + `top.v` 的例化与 CDC 位宽，
回滚方式为 `git revert` 该次提交；HyperRAM 布局变化不影响其他模块
（`0x00A0_0000–0x00BF_FFFF` 原本就只归掩膜使用），因此无跨模块数据迁移。

## Open Questions

1. **固件侧改造的具体形态**（本仓库无软核源码）：固件是继续复用 0xBB 帧协议加一个区域索引字段，
   还是沿用现有命令码只改目标地址？这不影响 RTL 契约、方案与任务分解，可在固件仓库内决定。
2. **上位机是否复用现有 `send_mask_via_adb.py` 流程**（该脚本不在本仓库）：
   同样属仓库外工作面，不影响本次 RTL 设计。
3. **`stall_count` 的精确上限取值**：spec 只要求"与每行至多一次冷缺失相符的低水平"。
   具体阈值待单元仿真跑出 4 路满尺寸的实际数据后回填，作为板级验收的判据。
