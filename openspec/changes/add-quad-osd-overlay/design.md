# Design

## Context

动机见 `proposal.md` — Why。此处只记录塑造方案的现状与约束。

**管线位置**：`VideoHorizontalFlipYuv422` → `HyperRamMaskOverlayYuv422` → `HyperRamVideoBt656`
→ `Adv7391Top` → CVBS。叠加模块工作在 `clk`（100 MHz），下游 BT.656 序列化在 `clk_da`（27 MHz），
两者之间的 CDC 由 `HyperRamVideoBt656` 内部的异步 FIFO 承担。

**当前实际生效的形态**（已核对 RTL，与部分文档不符）：

- `src/top.v:493` 将 `rtl_mask_mode` 硬接 `1'b0` → `raw_mode=0` → 模块走 **legacy 全屏分支**，
  从 `0x0040_0000`/`0x0050_0000` 读 720×576 画布。RTL 侧注释（`top.v:1774`）确认这是有意为之：
  软核把画布写进自己的工作区。
- `docs/architecture.md:286` 与 `docs/SOFTCORE_DESIGN.md:175` 却把该画布写在 `0x00A00000`。
  **RTL 是对的，文档是错的**（`top.v:1827` 的避让注释与 `SOFTCORE_DESIGN.md:598` 的链接脚本
  `ORIGIN = 0x00400000` 互相印证：画布与软核工作区共用同一段 HyperRAM，并非冲突）。
- `docs/architecture.md:283` 称"半透明掩膜"，但 `HyperRamMaskOverlayYuv422.v:161` 实际是
  **二值硬替换**（`mask_byte != 0` → `16'h80EB`）。**当前 RTL 没有 alpha**。

**缓存现状**（`HyperRamMaskOverlayYuv422.v:45-62, 115`）：2 个 bank × 256 字节乒乓缓存，
预取地址写死为 `next_block_addr = block_addr + 256`，**假定单一顺序行扫描**。
`src/top.v:158` 的 `s_ready = can_forward && m_ready` 意味着 cache miss 会直接阻塞视频流，
模块自身注释（`:47-50`）已警告这类阻塞可能撑爆 scaler 侧 CDC FIFO。

**控制现状**：`MaskControlRegs`（`0xE1043000`，`clk50M`/AXI 域）→
`ConfigSnapshotCdc #(.WIDTH(2))`（`top.v:1051`，`clk50M` → `clk`）→ `top.v:1431-1432` 的控制源 mux
→ 叠加模块。提交协议为 toggle + 帧边界 ack。`top.v:1085-1089` 有一段**3 拍 settle**，
其注释明确说明它存在的原因是"**叠加模块内部自带两级同步器**"——
即现有补偿逻辑是为模块内的同步级数量身定的。本变更删除模块内的同步器，该 settle 随之取消（D5）。

**资源现状**：两个 bank 是异步读，被 Efinity 映射到 logic memory 而非 BRAM
（`outflow/EFX.warn.log:77-78`，每 bank 2048 bit）。

**已有一份写成的实现（本次采纳为基线）**：`src/overlay/HyperRamMaskOverlayYuv422_4OSD.v`
（655 行，已随 `8c6b192` 入库，磁盘属性为只读，**且未登记在 `ivlab239.xml`**）是一份完整的
4 窗口叠加实现。它已经解决了本次变更最担心的两件事，因此**以它为基线、按 D1–D11 改造**
（见 D10），而不是从 `HyperRamMaskOverlayYuv422.v` 重写。它现成的部分：

| 已有能力 | 与本次决策的关系 |
|---|---|
| 11 级全寄存流水（S0..S10），级间组合逻辑 ≤ 5 级；两段推进式反压：域 1（S0..S6，遮罩字未捕获）在 cache 未命中时冻结等待 AXI，域 2（S7..S10，遮罩字已捕获）只要下游能收就继续排空 | 直接满足 D4 对"已完成的传输不被重复呈现"的 ready/valid 正确性要求 |
| 2 bank × 256 字节乒乓、16 拍 × 128 bit AXI 突发（ID 固定 `8'hA1`） | 与 D4"缓存不增长"一致 |
| 显式 `case(16:1)` 提取遮罩字节，规避 128 bit 桶形移位器 | 保留 |
| 有符号 16 位窗口坐标 + 越界裁剪（负坐标可用） | 与 D6 的负偏移裁剪一致 |
| 逐位独立 `mask_enable[3:0]`；重叠时按编号优先（0 最高） | 逐位独立保留；编号优先作为兜底保留（D10 第 9 项） |
| 1 bit/像素、行按 `width/8` 打包 | 与 D1、D3 同向，**无需改造**（但字节内位序是 LSB-first，需按 D10 第 12 项翻转） |
| 尺寸与基址为编译期 parameter | 与 D6"几何参数化"同向；但基址需由 4 个改为 8 个（D3） |

**需要改造的部分**见 D1（叠加色、位序）、D3（基址个数）、D5（buffer_select 与同步器）、
D6（参数约束与寄存器表）、D8（合并文件）、D10（逐项清单）。

**同一个 OSD 能力现在有三份并存、互不同源的实现** —— 这是本变更最容易踩空的地方，
所以先把边界写死。判据是"字形存在哪、由谁渲染"：

## Goals / Non-Goals

**Goals:**

- 4 路窗口在同一路视频上叠加；每路的**位置、使能、缓冲**运行时可配，
  **尺寸**由编译期参数定型。
- 位图带宽与容量降到 1 bit/像素的量级，缓存资源**不增长**，
  且不因窗口跳转引入超出预算的视频流阻塞。
- RTL 侧契约（区域地址 + 寄存器映射 + 位图格式）清晰到足以让固件与上位机独立实现。
- 菜单类 OSD（`0x04` UI 大类）的软硬分工确定下来，软核侧**复用**现有 C 代码而非重写。
- 顺带消除文档与 RTL 的两处失真，避免后续维护者被误导。

**Non-Goals:**

- 不引入 alpha 混合、半透明或彩色 OSD（决策：保持二值替换，叠加色为纯白）。
- **不做运行时改窗口尺寸**（决策：几何由参数定型；改尺寸需重新综合）。
- 不做硬件重叠**检测**与裁剪仲裁（决策：软件保证不重叠；硬件按编号优先仅作兜底，不入契约）。
- 不实现字符/字库渲染**硬件**（决策：字形合成在软核侧，硬件只消费位图）。
- 不改动软核固件的**业务逻辑**（源码在本仓库外），只定义它必须遵守的契约；
  但 `0x04` 协议的归属与复用策略属本变更范围（D11）。
- 不做 4 路窗口之间的 z-order 混合叠加。

## Decisions

### D1: 位图格式为 1 bit/像素，叠加色为纯白 `16'h80EB`

**选择**：位图 **1 bit/像素**，行内按字节打包（每行 `width/8` 字节，`width` 由参数给出且
必须能被 8 整除，见 D6）。bit = `1` → 输出 `16'h80EB`（Y=235 白）；bit = `0` → 视频像素透传。
行内 bit 顺序为 **bit 7 对应最左像素**。不引入 alpha。

**理由**：
- 叠加语义本就是二值键控，"画 / 不画"用 1 bit 表达已足够，8 bit 的多余 7 位从未被使用。
- 容量与取数带宽同步降 8 倍：`544×288` 一路一缓冲仅 **19 584 B**，
  4 路 × A/B 合计 **156 672 B**，在 2 MiB 区域内余量极大。
- **这是本次最实质的一条收益**：256 字节的 cache 块在 1 bpp 下覆盖 **2048 个像素**。
  544 宽时每行仅 68 字节，**一个块横跨约 3.8 行**；而 8 bpp 下每行 544 字节、每行需要 3 个块。
  块缺失频率下降约 15 倍，D4 的预取压力与阻塞预算随之大幅放宽。
- 与消费方形态一致：`ti60-osd-main` 的菜单本身就是单色位图
  （`OSD_PIXEL_FG 0xFF` / `OSD_PIXEL_KEY 0x00`），1 bpp 是它的自然形态。

**否决的替代方案**：
- *保持 8 bit/像素（只作零/非零判定）*：与现有上位机位图工具直接兼容，但用 8 倍容量与 8 倍取数
  压力换不来任何表达能力。工具侧把位图打包成 1 bpp 是一次性且机械的改造。
- *每像素 alpha*（用位图值做混合系数）：仍否决——会改变画面观感（出现半透明边缘），
  且需重新标定上位机生成的位图，超出本次范围。
- *全局 alpha 寄存器*：新增一个需要联调的寄存器，收益不明。

> **术语提醒**：本文件早期版本用"1-bit 替换"指**二值键控**（不是每像素位宽），
> 与现在这条"1 bit/像素"是两件事。本文件此后只用后者，读到旧表述请以本条为准。

### D2: 统一为 4 窗口逻辑，删除 legacy / raw 双寻址

**选择**：删除 `raw_mode`、`mask_left`、`mask_top` 端口与 `MASK0/1_BASE`、`RTL_MASK0/1_BASE`、
`RAW_MASK_*` 参数，以及 `HyperRamMaskOverlayYuv422.v:91-108` 的双寻址分支。
4 路窗口用同一套"基址 + 行跨距 + 窗口内偏移"寻址。

**理由**：用户选择"完全替换为 4 路"。两套寻址并存会让地址生成逻辑出现两条近似路径，
而 legacy 分支的"输出边界即画面边界"恰好是 4 窗口逻辑在窗口等于全屏时的特例，
统一后总逻辑量反而下降。

**否决的替代方案**：
- *保留 legacy 并存*：逻辑与寄存器最复杂，且 legacy 分支当前是唯一生效路径，
  保留它等于保留一个必须同步维护的第二套行为。
- *legacy 降级为占满全屏的窗口 0*：行为兼容性最好，但用户明确要求"完全替换"，
  且 544×288 的上限让"全屏窗口"（720×576）无法用同一套参数表达，反而要引入特例。

### D3: 内存布局与行跨距

**选择**：位图区 `0x00A0_0000–0x00BF_FFFF`（2 MiB），**8 个固定基址**：

`base(i, buf) = (buf ? 0x00B0_0000 : 0x00A0_0000) + i * 0x0004_0000`

| 路 | Buffer A | Buffer B |
|---|---|---|
| OSD0 | `0x00A0_0000` | `0x00B0_0000` |
| OSD1 | `0x00A4_0000` | `0x00B4_0000` |
| OSD2 | `0x00A8_0000` | `0x00B8_0000` |
| OSD3 | `0x00AC_0000` | `0x00BC_0000` |

**行跨距紧凑取 `width/8` 字节**（不再使用固定 512 字节）。寻址式：

```
byte_addr(x, y) = base(i, buf) + y * (width_i / 8) + (x >> 3)
bit_index       = 7 - (x & 7)          // bit 7 最左
```

**理由**：
- 1 bpp 下紧凑跨距的容量代价已经归零：`544×288` 一路一缓冲 19 584 B，
  即使按 512 跨距也只占 147 456 B——为省内存而选择固定跨距已无意义。
- 紧凑跨距使**一路位图在内存中连续**（`row y+1` 紧接 `row y`），
  于是"窗口内扫描序 = 内存线性序"。这条性质是 D4 预取规则得以简化的根据。
- 基址固定为 8 个常量参数（在 `top.v` 例化处以字面量传入），**不提供运行时基址寄存器**。
  虽然几何参数化后 `B = A + width*height/8` 在展开期是可计算的，但仍选择 8 个独立基址：
  让 B 基址依赖宽度，等于让"改一个尺寸参数"隐式移动已上传的 B 缓冲内容，
  上传方（上位机/软核）将不得不跟着改地址。固定 8 个基址把两者解耦。
- 具体后果：消费方的运行时基址寄存器需求被否决，见 D10 第 10 项与 D11。

**否决的替代方案**：
- *保持固定 512 字节跨距*：1 bpp 下每行仅用 68/512 字节，浪费 7.5 倍，
  且失去"位图连续"这条让 D4 简化的性质。
- *运行时基址寄存器*：让消费方可任意摆放画布，但要引入 4 路 × 2 缓冲共 8 个需要同步的 32 位地址，
  并让地址生成路径多一级 mux；固定基址把这块风险降到 0。
- *只给 2 个基址 + `B = A + W*H/8` 推导*：省 6 个参数，但引入了上面说的隐式耦合。
- *放 `0x0040_0000`（软核工作区）*：需与固件协商边界，耦合度高。

**已决：槽位间距维持 256 KB，不收紧**。代价是每路每缓冲实际只用 19 584 B 却独占 256 KB 槽位，
利用率 7.5%；多余空间留作余量，换取基址表长期稳定、不随尺寸参数变动。

### D4: 缓存不变，预取地址推广为"扫描序下一块"

**这是本次变更的核心设计。**

**选择**：保持 2 bank × 256 字节乒乓缓存与 16 拍 AXI 突发**完全不变**，只把
`next_block_addr = block_addr + 256` 替换为按优先级计算的"扫描序下一块"：

1. 当前窗口位图在扫描序上还有后续字节 → `block_addr + 256`
2. 否则本行存在更靠右的使能窗口 → 该窗口本行起始字节所在的块
3. 否则下一显示行中首个使能窗口的起始字节所在块（因 `FLIP_VERTICAL_COORDS=1`，下一行 = `display_y - 1`）
4. 否则不预取

**1 bpp 让规则 2/3 变得很少触发**：块覆盖 2048 像素，544 宽时一个块横跨约 3.8 行，
只有扫描真的跨窗口边界时才需要规则 2/3；规则 1 承担绝大多数情况。

**理由**：
- 窗口**两两不重叠**（D5 的软件保证），所以任一像素至多属于一个窗口 → 2 bank 乒乓依然成立，
  **缓存容量与逻辑 RAM 占用不变**（维持 4096 bit）。
- 每次预取都在消费前一块的**同时**发起，块消费耗时 = 2048 像素（1 bpp）远大于一次 256 字节
  AXI 突发，隐藏取数延迟的余量比 8 bpp 时更宽。
- 规则 3 让行与行之间也预热，把冷缺失压到"整个帧第一行"级别。

**行偏移保持常量乘**：`_4OSD.v:567-570` 的 `s4_rowoff <= s3_srcy * BPRn`
（`BPRn = OSDn_WIDTH/8`）**原样保留**。这是 D6"几何参数化"带来的直接好处——
`width` 不进运行时寄存器，`BPR` 就仍是 localparam，乘法仍是常量乘，
既不需要乘法器，也不需要"行起始累加"这类替代结构。**这是选择参数化几何的主要技术理由。**

**否决的替代方案**：
- *每路一个独立 bank（4 或 8 bank）*：地址判定最简单，但逻辑 RAM 翻 2–4 倍
  （现有 2 bank 已被映射到 logic memory），8 bank = 16 384 bit，对 Ti60 是实质新增压力。
- *每路一个行缓冲*：同样 16 384 bit，且宽度小时浪费更多。
- *不做预取，miss 时才取*：直接复现模块注释警告的逐 miss 阻塞，
  4 路窗口会让每行出现多次阻塞，有撑爆 scaler CDC FIFO 的实际风险。

### D5: 单次 commit + 单次 apply，每路独立 buffer_select，配置直连

**选择**：
1. 每路各有自己的 `buffer_select` 与 `enable` 位（不再 4 路共用）。
2. 沿用**一套** `ConfigSnapshotCdc`（`WIDTH` 由 2 加宽到 **105**）与**单一**提交/生效时点
   （仍在 `flip_output_sof` 处应用）。
3. **删除 `_4OSD.v` 模块内的配置同步器**（`enable_meta/sync`、`pos*_meta/sync`、`buffer_sync`），
   配置由快照直连。
4. 因此**删除 `top.v:1085-1089` 的 3 拍 settle 逻辑**，`mask_cfg_apply` 简化为
   `pending && flip_output_valid && flip_output_sof && mask_input_ready`。

**理由**：用户要求"每路独立 A/B"，"原子提交"避免 4 路版本不一致的中间帧——
这是 OSD 这类叠加层不可接受的观感缺陷。而原子性只有**单点生效**才名副其实：
`_4OSD.v` 原状是 4 路共用一个 `buffer_select`，且模块内 4 组独立同步器各自采样、
无帧边界锁存，同步过去立即生效，正是要消除的撕裂源。

**位宽构成**：每路 `1 enable + 1 buffer + 12 left + 12 top = 26`，4 路 = 104，
加 `1 global_enable` = **105**。`width`/`height` **不进快照**（它们是编译期参数）。

**为什么可以删掉模块内同步器**：`ConfigSnapshotCdc` 本就承担 `clk50M` → `clk` 的跨域，
它输出的 `dst_data` 已在 `clk` 域且按多位原子快照更新。模块内的第二级同步器是历史遗留
（`top.v:1085-1089` 的 3 拍 settle 就是为补偿它而写的），删掉它之后 CDC 责任单一，
`top.v` 反而更简单。**代价是这条改动动了既有 `top.v` 的补偿逻辑，必须在仿真中验证帧边界原子性**
（见 Risks 与任务 4.3、7.4）。

**否决的替代方案**：
- *保留模块内 2 级同步器、保留 3 拍 settle*：改动最小，但保留两级不同步的同步链，
  且 4 组独立同步器各自采样，原子性依赖"源数据在 apply 前已稳定 ≥ 3 拍"这一时序约定。
- *每路一套 CDC、独立 apply*：4 倍同步逻辑，且允许 4 路在不同帧生效，
  会出现"部分 OSD 新版、部分旧版"的中间帧。

### D6: 编译期几何参数与寄存器映射

**选择（一）编译期参数**：每路的尺寸与基址由**参数**给出，不进寄存器。

| 参数 | 含义 | 约束 |
|---|---|---|
| `OSD0..3_WIDTH` | 该路位图宽度 | `% 8 == 0`，`≤ 544` |
| `OSD0..3_HEIGHT` | 该路位图高度 | `≤ 288` |
| `OSD0..3_BASE_A/B` | 8 个固定基址 | D3 表的值 |

约束 SHALL 以展开期检查实现，使非法尺寸在综合阶段暴露，而不是静默产生错位画面。

**实现机制（已落地）**：参数非法时例化一个**不存在**的模块，名字即诊断信息
（如 `OSD2_HEIGHT_must_be_within_1_to_288`）。这比 `$error` 更早生效 ——
`$error` 写在 initial 块里要到**运行期**（时刻 0）才触发，编译照样通过；
而这里要挡住的正是"编译能过、上板才发现画面错位"。
另注：`vlog` 只做编译不做完整展开，所以该检查在 **`vsim` 展开期与综合期**报错，
不在 `vlog` 期 —— 验证时用 `vsim`（任务 2.3 的实测即如此）。

**选择（二）寄存器映射**：在 `MaskControlRegs`（`0xE1043000`）内扩展，共 **12 个字**：

| 偏移 | 名称 | R/W | 内容 |
|---|---|---|---|
| `+0x00` | `COMMAND` | W | bit31 commit，bit0 global_enable |
| `+0x04` | `STATUS` | R | `{commit_count[15:0], 13'd0, pending, 1'b0, applied_global_enable}` |
| `+0x08` | `CANVAS` | R | `{16'd720, 16'd576}`（保持原样） |
| `+0x0C` | `ACTIVE` | R | `{24'd0, applied_enable[3:0], applied_buffer_select[3:0]}` |
| `+0x10 + 8*i + 0x0` | `OSD[i].POS` | W | `{8'd0, top[11:0], left[11:0]}`，均为**有符号** |
| `+0x10 + 8*i + 0x4` | `OSD[i].CTRL` | W | `{30'd0, buffer_select, enable}` |

地址范围 `+0x00..+0x2F`。

**理由**：
- 沿用既有 commit 语义（写 COMMAND bit31 才发布；`pending` 未清时拒绝再次 commit），
  上位机现有的"写寄存器 → 提交 → 轮询 pending"流程无需改结构。
- `left/top` 取**有符号 12 bit**，保留 `_4OSD.v` 已有的**负偏移越界裁剪**能力，
  上位机可把窗口部分移出画面而不必自己做裁剪。
- 尺寸改由参数定型后，寄存器表从 20 字缩到 12 字，`pending` 期间需要保持稳定的位变少，
  提交协议本身也更简单。
- 12 个字远在现有一拍 AXI 端点的 `read_addr[11:2]` 可寻址范围内。
- **不提供编译期几何的回读**（已决）：表里既没有 `SIZE`，也不新增只读 `GEOM[i]` 之类的镜像。
  几何对齐完全依赖契约文档移交（任务 9.4）与固件配置；规格表述见 spec 的
  "控制寄存器契约" Requirement（系统 SHALL NOT 提供窗口尺寸寄存器）。
  代价是上位机无法从 RTL 侧自查位流用的是哪组尺寸，这一风险已在 Risks 中记录。

**`_4OSD.v` 中被本映射取代的接口**：四组 `OSDn_BASE_A/B` 由 4 个改为 8 个参数（D3）、
`mask_enable`/`mask_buffer_select` 端口与 `mask_0..mask_3` 的 `{left[31:16], top[15:0]}`
打包端口由快照驱动（left/top 收窄为 12 bit，见 D10 第 8 项）。
`OSDn_WIDTH/HEIGHT` 与 `localparam BPRn` **原样保留**。

### D7: `rtl_mask_mode` 语义收窄

### D10: 采纳 `_4OSD.v` 为实现基线，并列出逐项改造清单

| # | 现状 | 目标 | 依据 |

| 12 | `pbitsel[4] <= s3_srcx[2:0]` —— 字节内 **LSB 为最左像素** | 改为 `3'd7 - s3_srcx[2:0]`，使 **bit 7 为最左** | D1 |
| 13 | `next_block = {s6_byteaddr[31:8] + 24'd1, 8'b0}` —— **内存序**的下一块 | 改为 D4 的**扫描序下一块**（规则 1–4） | D4 |

> **第 13 项也是实现阶段新发现的偏差**，而且它是本变更**最核心**的一条（D4 原文自己写着
> "这是本次变更的核心设计"）。本清单的早期版本把"扫描序预取"错误地归进了第 11 项的
> "保留不变"里 —— 实际合并进来的实现只有**内存序**的 `block_addr + 256`，
> D4 的规则 2/3（跳到本行更靠右的窗口 / 下一行首个窗口）完全不存在。
>
> 后果已用测试平台的突发计数器量化（全尺寸一帧、每个突发 256 字节）：
>
> | 使能的路 | 布局 | AXI 突发数 |
> |---|---|---|
> | `0001` | 单路 | **17**（一帧下限 = 16 块 + 1 预取） |
> | `0101` | 两路，不同行带 | **34** |
> | `0011` | 两路，**同行带并排** | **512** |
> | `1111` | 四路，两两并排 | **1024** |
>
> 同行带的两路会让 2 bank 缓存**每行都换出重读**（256 字节的块只消费 8 字节），
> 比下限差 15 倍、一帧多读约 122 KB。这正是 D4 要解决的问题。

> 第 12 项是**实现阶段新发现的偏差**，不在本文件最初的 11 项里。它是核对 `_4OSD.v`
> 的字节提取路径时发现的：`s8_byte[pbitsel[8]]` 直接用 `dx[2:0]` 作位号，
> 于是 `dx=0` 取 LSB，与 D1 定的 MSB-first 相反。收益不只是"合规格"——
> 改成 MSB-first 后 `composer.c` 的 1bpp 打包变成**直接搬字节**（ti60 的
> `font_row_bits()` 本来就是 bit15 = 最左），两个位反转一起消失。

**理由**：这份实现已经解决了本次变更最核心的两个工程风险——流水级数与两段式反压的正确性、
预取与取数延迟的隐藏——且微架构已被逐行核对（见 Context 表）。从零重写等于把这些风险
重新引入一次，而它需要改的 13 项里有 3 项是"明确保留"，实际改动分散在接口、常量与预取策略三处 ——
其中第 13 项（扫描序预取）是工作量与风险最大的一项，也是本变更的核心，
不动流水骨架。

### D11: `0x04` UI 大类协议并入本变更；权威是"文档 + 工具"，不是 ti60

**先纠正一条事实**：本文件上一版把 `ti60-osd-main` 当作 0x04 协议的参照实现。核对后确认
它只是**三份实现中的一份，且是三份里最偏离线上契约的一份**。权威口径有且只有两份，
且互相一致：

- `docs/x2000_ui_protocol.md`（§2 公共报文、§3 状态命令、§4 稳定页面 ID）
- `tools/send_ui_via_adb.py`（上位机工具，`:99-107` 的校验是逐字节的）

两者在应答长度上完全一致，而 `ti60-osd-main` 不一致（见下表）。因此本变更的口径以前两者
为准；`ti60-osd-main` **只提供构图机制的代码**，其协议层（`proto.c`、`dispatch.c`）与
应答布局一概不采用。

**选择（一）应答口径**

| 子项 | 应答整帧 | body | 依据 |
|---|---|---|---|
| `0x08` QUERY_VIEW | **18 字节** | **12** = `04 08 02 FF` + `page_id(2)` + `sel` + `flags` + 4 个数值 | `doc` §3.3、工具 `:99` `18 if sub==8` |
| 其余子项 | **10 字节** | **4** = `04 sub 02 status` | `doc` §2、工具 `:99` `else 10` |

- 成功判据是 `body[3] == 0xFF`（工具 `:106` 硬校验），失败为 `0x00`。
- CRC 覆盖完整 body（`doc` §2）：QUERY_VIEW 覆盖 12 字节，其余覆盖 4 字节。
- **10 字节这一支与 `protocol_build_ack()` 的现有输出逐字节相同**（含 CRC 覆盖范围与
  `PROTOCOL_STATUS_OK = 0xFF`），一行都不用改；只有 QUERY_VIEW 需要新的变长构造。

**选择（二）`flags` 三位**

`bit0` = UI 显示、`bit1` = 进入数值编辑状态、`bit2–7` 保留位**静默丢弃**（不报错）。
依据：`doc` §3.1 + 工具 `:87`（只发 bit0/bit1，从不动 bit2）。

> 这里与 `doc` §3.1 原文"其余 flag 必须为 0"（配合同节末句"flag 非法时返回失败"）
> **不一致** —— 已决**保留** `ui.c:164` 的宽容行为（`flags & UI_FLAG_MASK`，保留位忽略），
> 改为在**文档侧**说明。任务 9.7 记录该文档修订。

**选择（三）代码归属**

`protocol.*`（ivlabSoftCore）**新增** 0x04 分支：沿用其现有的表驱动风格，与掩膜表并列一张
UI 子项表（长度校验同样由表结构承担），handler 调 `ui_set_view` /
`ui_set_image_values` / `ui_query_view`。**不搬运、不替换** `ti60-osd-main` 的 `proto.c` 与
`dispatch.c` —— "串口与协议处理代码不动"指的就是"不被这两份实现替换"。

`frame.h` 已备好 `FRAME_CATEGORY_UI 0x04`（`:79`，注释"UI 菜单 —— 其他模块负责"），
需新增子项常量。

**选择（四）统计口径**

0x04 从 `other_category_count` 移入 `accepted_count`（坏 CRC 仍计 `bad_packet_count`）。
理由：`other_category_count` 的设计意图是诊断"链路上还有谁在说话"（`protocol.h:73`），
0x04 成为本端点职责后继续计入会让该指标失真。

**选择（五）提交后才应答成功**

`doc` §5.5：「TI60 在完成字符页非活动 bank 写入并**提交后**才返回成功」。
因此 `SET_VIEW` / `SET_IMAGE_VALUES` 的**成功** ACK 不能在解析后立即发，须挂起到主循环
完成 `composer_render()` + `canvas_commit()` 之后再发；**失败**（参数非法）可立即回
`status = 0x00`，无需渲染。`canvas_commit()` 自身是"置位立即返回"（C-7 已决），
所以等待的是"写完 + 置位"，与 §5.5 的"提交后"吻合。

**选择（六）`bit0` 与窗口使能的联动**

`flags.bit0`（UI 显示）落到实处就是**菜单承载路**（D3 表第 2 行，即 `OSD[1]`）的 `CTRL.enable`。这是"UI 状态"与 D6 寄存器契约的
接口点：软核提交 SET_VIEW 时一并写该位；子项 `0x01`（show/hide）落在同一处。

**选择（八）位图上传只写固定的一路**

上传协议**不增加区域索引字段，也不以目标地址表达区域选择** —— UART 上传路径固定写一路，
其余路的缓冲内容逐字节不变。`RtlMaskUartAxiWriter` 同理。软核作为软件仍可寻址任意路
（它本来就能算地址），但那不经由上传协议。

**理由**：帧格式保持不变，上位机工具与软核都只需改位打包（而位打包本次反正要改，
见 Open Questions 的收官记录），不必在两条上传路径上同时扩展字段与长度校验；
而"协议上能上传到 4 路"这件事并没有实际需求 —— 多路场合由软核直接寻址。

**推论（必须遵守）**：上传固定路与菜单承载路**必须是不同的两路**，否则上传会覆盖菜单画布。

**窗口划分**：按最小改动取值 —— 上传固定路取 D3 表的**第 1 行**（现有
`RtlMaskUartAxiWriter` 用的正是 `RTL_MASK0_BASE = 0x00A0_0000` / `RTL_MASK1_BASE = 0x00B0_0000`，
这样它的基址一行都不用改），菜单因此取**第 2 行**：

| 用途 | D3 表行 | Buffer A | Buffer B |
|---|---|---|---|
| 掩膜上传固定路 | 第 1 行 | `0x00A0_0000` | `0x00B0_0000` |
| 菜单承载路 | 第 2 行 | `0x00A4_0000` | `0x00B4_0000` |

菜单尺寸参数取 **544×208**（菜单框本身），落在 D6 的 544×288 上限之内。其余 2 路留给别的用途。

**选择（七）本期范围界定**

的关系 —— 它的坐标范围 11..708 / 11..564 正是画面内缩边界的形状。

**后续接入 26 页 cp1251 菜单时会遇到的两件事**（本期不做，记录以免将来当成缺陷）：

1. **生成器输出路径**：`tools/generate_ui_menu.py:5` 的 `SOFT` 写死为
   `D:\Desktop\szkriscv_tongyi_dpc\...\ivlabIspSoftCore\src`（本机不存在），因此 26 页菜单
   无法从本检出重新生成。接入前需把该路径参数化，并把生成产物纳入版本控制。
2. **需要一层 cp1251 → Unicode 码点映射**：生成器产出的是 **cp1251 字节**（`cbytes()` 用
   `encode("cp1251")` 写进 `text[33]`），而 ti60 的 `font_lookup()` 吃的是 **Unicode 码点**
   （`utf8.h` 负责 UTF-8 → 码点）。两者之间差一层 128 项左右的映射表（cp1251 的
   `0xC0`–`0xFF` → `U+0410`–`U+044F`）。本期菜单数据直接用 ti60 的 `scene_table.c`
   （已经是码点形式），不涉及这一步。

**顺带记录一处将来的张力**：产品菜单最终是俄文，而 `flags` 不承载语言（选择（二））——
语言入口不存在于本协议。本期菜单走 ti60 的英文串（`ui.c:32` 固定 `en`）不受影响；
将来做俄文菜单时，"用哪套字符串"需要一个协议外的约定。

**跨变更影响（须处理）**：`add-softcore-uart-app` 的 `softcore-uart-protocol` spec 当前规定
"**只有掩膜大类 `0x00` 被处理并应答**，其它大类只解析、不应答、不计入坏包"，
与 D11 直接冲突。口径现已明确（见上文），该 spec 需修订为按子项区分应答长度。
**那是另一个变更的 spec 文件，本文件只记录该结论**，落地归属见 Open Questions 1。

## Risks / Trade-offs

- **几何参数化后，位流参数与工具/固件假设不一致会静默错位** →
  接口仍在、画面却错，且无任何错误反馈。缓解：把 8 个尺寸参数与 8 个基址作为契约的一部分
  书面移交（任务 9.4/9.5）。**已决：不提供几何回读**（D6），因此这条风险无法由 RTL 侧自查，
  只能靠移交文档与固件配置的准确性来消除。
- **1 bpp 破坏上位机与 RTL 上传路径的现有字节语义** →
  现有位图生成工具产出 8 bit/像素，`RtlMaskUartAxiWriter` 按字节直写画布；
  改为 1 bpp 后两者都要做位打包。缓解：把"1 bpp、行按 `width/8` 打包、bit 7 在左"
  作为 spec 级契约固定；**工具与 RTL 同批改**（任务 5.1/5.3，工具已在检出内），
  软核侧随固件改造一并做。
- **上传固定路与菜单承载路若配成同一路，上传会静默覆盖菜单画布** →
  D11 的窗口划分已把两者分到 D3 表的第 1 行与第 2 行，但这是**参数层面**的约定，
  硬件不会检查。缓解：把"上传路 ≠ 菜单路"写进 spec（"位图上传路径"Requirement），
  并在板级验收时用一次上传后目视确认菜单未变（任务 8.5/8.6）。
- **删除模块内同步器 + 删除 3 拍 settle 是对既有 `top.v` 补偿逻辑的实质改动** →
  若 `ConfigSnapshotCdc` 的 `dst_data` 稳定性不满足要求，会出现配置位不一致的中间态。
  缓解：单元仿真显式断言帧边界原子性（只切换第 2 路时其余三路逐像素不变），
  再进综合与板级；仿真不便时退回"保留同步器 + 保留 settle"这一改动更小的分支。
- **预取规则 2/3 组合逻辑变深** → 在 100 MHz 下新增了跨 4 路的比较与 mux。
  缓解：先在单元仿真确认功能，再在 Efinity 综合后复核 `docs/timing_resources.md` 的时序余量；
  若紧张，可把"下一块地址"打一拍寄存（预取本就提前发起若干拍，寄存不影响正确性）。
- **逻辑 RAM 未增长但组合逻辑变复杂，可能改变 Efinity 的映射结果** → 缓解：
  综合后对照 `outflow/EFX.warn.log` 确认两个 bank 仍被识别为 memory block，未被展开成触发器。
- **8 个基址槽位利用率仅 7.5%**（每槽 19 584 B / 256 KB）→ 已接受，
  且**已决不收紧间距**（D3）：换取基址表长期稳定。
- **软件保证不重叠是一个"契约外"的约定** → `_4OSD.v` 的编号优先仲裁提供兜底，
  但兜底会掩盖上位机的配置错误，且几何固定后重叠完全由**运行时位置**决定。
  缓解：`ACTIVE` 回读每路实际生效的使能与缓冲（几何可由位流参数静态推定）；
  重叠校验在上位机侧实现（仓库外工作）。
- **删除 legacy 全屏掩膜破坏向后兼容** → 缓解：见 Migration Plan；这是明确要求的破坏性变更。
- **固件源码不在本仓库，契约可能落地不一致** → 缓解：把区域地址、寄存器映射、位图格式
  （1 bit/像素、紧凑跨距 `width/8`、bit 7 在左）与编译期几何作为 spec 级契约固定下来；
  固件侧改造列为外部依赖并在验收时联调两条路径。
- **`ConfigSnapshotCdc` 从 2 bit 加宽到 105 bit** → 宽快照的同步链更长、面积更大，
  但该模块本就是为多位原子快照设计的。缓解：仿真验证帧边界原子性（同第 3 条）。
- **`0x04` 协议跨越两个变更** → 若 `add-softcore-uart-app` 的 spec 不修订，
  两份 spec 会直接互相否定。缓解：把修订列为本变更的前置或并行项（Open Questions 1）。
- **三份实现并存，规格来源极易串用**（Context 的对照表）→ 本期已用"按 ti60"钉死字体与
  栅格（选择（七）），但**将来接入 26 页 cp1251 菜单时串用风险会回来**：那时字库要覆盖西里尔、
  菜单数据来自生成器、两者之间还差一层 cp1251 → 码点映射。缓解：本文件已把这三件事的出处
  与差异逐条写明；接入时按该段执行，不要再从 ③ 直接取规格。
- **不纳入的 sub `0x01`–`0x05` 会让上位机工具的五个模式超时** →
  `tools/send_ui_via_adb.py` 对**所有**子项都期待应答（`:99`），因此 `--show`、`--hide`、
  `--key`、`--clear`、`--marker` 与无参数的默认模式（sub 3）在联调时会挂住到超时。
  缓解：任务 8.6 只跑本期可用的三条路径；并在移交文档里写明这五个模式的现状，
  避免现场把它当成故障。**`0x01` show/hide 不纳入不造成能力缺口** —— 显示/隐藏由
  `SET_VIEW` 的 `flags.bit0` 承担。
- **`SET_IMAGE_VALUES` 按"仅显示状态"实现（已决）** → 若现场实际要求 TI60 施加对比度/亮度/
  图像增强，现有 4 个 `*ControlRegs` 块与视频管线都没有落点，那是新寄存器块 + 新变更的规模。
  缓解：spec 已把该假设写成显式条款（`SHALL NOT` 施加到硬件），一旦需要改变即为契约变更，
  不会被当成实现遗漏。
- **菜单数据的产出链路不在本仓库**（后续问题，不在本期关键路径）→
  `tools/generate_ui_menu.py:5` 的输出路径写死为 `D:\Desktop\szkriscv_tongyi_dpc\...`
  （本机不存在），26 页菜单无法从本检出重新生成。本期只做 ti60 的 3 页骨架，故不阻塞；
  接入 26 页前须先把该路径参数化并把生成产物纳入版本控制。

## Migration Plan

1. **RTL 先行**：合并文件（D8）→ 改 `HyperRamMaskOverlayYuv422.v`（D10 的 11 项）
   + `MaskControlRegs.v`（D6）+ `top.v`（例化、CDC 位宽 2→105、删除 3 拍 settle、控制源 mux 与注释）。
   此时旧上位机不再能配置 legacy 全屏掩膜（该功能按设计移除）。
2. **单元验证**：新写自检测试平台（`sim/` 当前为空）通过后，再进综合与板级。
   重点是帧边界原子性（D5 的改动风险最高）与预取阻塞预算。
3. **板级验证**：按 `docs/CLAUDE.md:255-263` 清单回归，并通过 VIO 观察新增诊断。
4. **工具与固件同步**：按 D6 寄存器映射、D3 内存布局、D1 位图格式改造；
   两条上传路径各联调一次。
5. **`0x04` UI 协议**（范围已定，见 D11 选择（七））：
   在 `protocol.*` 新增 0x04 子项表（只 `0x06`/`0x07`/`0x08`）→ 接入复用后的构图层
   （含 D11 的 8 项改动，字体与栅格按 ti60）→ 主循环加"渲染 + 提交 + 延后应答"的状态
   → 完成 `add-softcore-uart-app` 的 spec 修订。
6. **文档收尾**：完成 D9 的文档修正（含内存表按 1 bpp 重写），
   以及 `docs/x2000_ui_protocol.md` §3.1 关于"保留 flag 静默丢弃"的补充说明（任务 9.7）。

**回滚**：改动集中在 3 个 RTL 文件 + `top.v` 的例化、CDC 位宽与 settle 逻辑，
回滚方式为 `git revert` 该次提交；HyperRAM 布局变化不影响其他模块
（`0x00A0_0000–0x00BF_FFFF` 原本就只归掩膜使用），因此无跨模块数据迁移。
`_4OSD.v` 被删除后其内容已并入主文件，回滚会一并恢复。
